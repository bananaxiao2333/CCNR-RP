# P16 玩家属性（docs/16）

> 对应 issue #2「增加玩家属性编辑器」的落地部分。原 issue #3「特殊按钮」当时落成"区域 + 弹头许可"，
> 在 2.25.0 已整体删除并改由 **自定义设定（变量系统，docs/17）**承载——本 mod 只发布事实与判定，功能本体在外部。

## 1. 需求与边界

- **issue #2**：能在管理界面按阵营编辑该阵营玩家的属性（如血量），出门是满状态；需适配 FirstAid。
  维护者定调：**先原版属性，再扩展 mod；必须解耦**（不能重演 better_looting / corpse 那类兼容事故）。
- **issue #3**（历史）：当时需要在阵营管理界面增加"是否可以启动弹头"；维护者定调：**核弹功能非本 mod 内容**。
  2.24.0 的落地方案（「拓展设定」页签 + 区域注册表 + `warheadEnabled`/`warheadArea`）在 2.25.0 已**整体删除**：
  该需求改由**自定义设定（全局变量系统）**承载，见 docs/17。安全/突袭的"类原版按钮触发机制"**暂不采纳**（等对局状态机完善）。
- 本仓库的交付边界：
  1. 阵营属性配置（原版属性 + 任意 mod 属性，按注册名寻址）+ 管理面板编辑器 + 命令 + FirstAid 适配；
  2. **不做**：核弹发射逻辑、弹头实体/爆炸/倒计时、区域/坐标判定、对 CCNR-Com / CC-api 的任何调用或依赖。

## 2. 阵营属性

### 2.1 数据（`config/ccnr_rp/factions.json`）

```json
{
  "id": "qdf",
  "name": "QDF司令部",
  "attributes": [
    {"id": "minecraft:generic.max_health", "amount": 40, "operation": "add"},
    {"id": "minecraft:generic.armor", "amount": 4, "operation": "add"},
    {"id": "minecraft:generic.movement_speed", "amount": 0.1, "operation": "multiply_base"}
  ]
}
```

- `id` 一律写**属性注册名**（`namespace:path`）；`operation` ∈ `add` / `multiply_base` / `multiply_total`
  （缺省 `add`）；单阵营上限 16 条（`AttributeProfile.MAX_ENTRIES`）。
- 字段可选；缺省 = 无属性加成。解析/校验在**纯类** `AttributeProfile`（无 MC import，可脱机单测）：
  非法 id / 未知运算 / 非有限数值 / 血量加法非正 / 超上限 → 拒绝保存且**不做部分提交**；
  同（id+运算）重复声明 → 后者覆盖 + WARN。
- 结算顺序与原版一致：`v = (base + Σadd) × (1 + Σmultiply_base) × Π(1 + multiply_total)`（纯函数 `resolve`，可测）。

### 2.2 套用时机（唯一入口 `AttributeService`）

| 时机 | 行为 | 为什么 |
| --- | --- | --- |
| 部署（`SpawnFramework.applyDeployCore`） | 清背包后、`resetPlayerState` **之前**套用 | `resetPlayerState` 用 `getMaxHealth()` 回满；顺序反了会按旧上限回满（改血量后出门不是满状态） |
| 登录（`CCNRRPMod.onPlayerLoggedIn`，在场玩家） | 按当前配置重套 | 永久修饰随存档保留，重连后与配置对齐 |
| 管理面板/命令保存 | 该阵营**在线**成员立即重套 | 服务端权威 + 所见即所得（docs/01 §11.2） |
| 退场（死亡/判死/退役/疏散/旁观兜底/归一化） | 统一入口 `StatusManager.purgeOnObserving` → `AttributeService.clear` 卸下修饰（同时清背包） | 观察者不带上一局的加成与装备；见 docs/05 §2.1 |

- 幂等：本 mod 施加的修饰名一律带 `ccnr_rp:attr:` 前缀，套用前先清理同前缀修饰（确定性 UUID + 前缀清理），
  重复部署/换阵营/重连都不会叠加成第二份加成。
- **未注册 id 不算配置错误**：执行期跳过并 WARN（"装对应 mod 后生效"）。这是"原版优先、mod 自然扩展"的解耦点——
  适配层不认识任何具体 mod，只认注册名。

### 2.3 FirstAid 适配（为什么需要、怎么保证不炸）

FirstAid（modid=`firstaid`）把原版血量换成 **8 个部位各自的血量上限**：原版 `generic.max_health`
只被它用于显示钳制（`SynchedEntityDataHelper` 里 `min(原版血量, max_health)`），
真正的伤害与死亡判定走部位血量。所以"改血量"必须翻译成**缩放部位血量上限**：

- 倍率 = `resolve(attributes, "minecraft:generic.max_health", 20) / 20`；对每个部位
  `setMaxHealth(round(initialMaxHealth × 倍率))` 后 `heal(上限)` → **出门即满状态**；
- 未配置血量时按 `initialMaxHealth` **复位**（换到无属性阵营不会残留上一阵营的放大血量）；
- 适配层是 `PlayerAttributeBridge` 内的私有内部类，**纯反射**（capability 静态字段 + `getMaxHealth`/
  `setMaxHealth`/`heal` 三个公开方法）+ `ModList.isLoaded("firstaid")` 探测 + 全程 `try/catch Throwable`：
  **不引入任何编译期依赖**（不新增 mods.toml 依赖、不新增 libs/ jar、不动 CI 取依赖流程），
  与 `CamSceneBridge`（CMDCam）同一套"可选依赖、缺失降级"纪律。
- **如何失效**：FirstAid 改 API → 反射失败 → 记一次 WARN，属性其余部分照常生效，血量保持 FirstAid 原值；
  不崩服、不改一半。若要类型安全，可后续按 docs/01 §8 为它补 `compileOnly` jar + fetch 脚本（届时需同步 mods.toml 与 ProjectMetadataTest）。

### 2.4 角色（职业）层属性：同 id 覆盖阵营层（2.26.8）

**层级**：`阵营层`（`factions[].attributes`）→ `角色=职业层`（`professions[].attributes`，同一份 `factions.json`）。
职业层**覆盖**阵营层，**判定键 = 属性 id**：只要职业层声明了某个 id，阵营层该 id 的
**全部运算条目**都被取代（不是按 `(id+运算)` 逐条覆盖，也不是叠加）。

```json
"professions": [
  { "id": "qdf_guard", "name": "QDF队员", "factionId": "qdf",
    "attributes": [ { "id": "minecraft:generic.max_health", "amount": 60, "operation": "add" } ] }
]
```

- **为什么按 id 整体覆盖**：把两层不同运算（阵营 `add 40` + 职业 `multiply_base 0.1`）叠在一起既没有
  直觉上的意义，也不好向管理员解释；"同 id 整体接管"是最容易预期的行为。规则与判据都收在纯逻辑
  `AttributeProfile.layer(factionEntries, professionEntries)`（返回生效条目 + **被覆盖的 id 集合**）。
- **未声明的照旧继承**：职业层没写的 id 从阵营层取；职业层新写的 id 属于**新增**，不计入覆盖集合
  （界面/命令不会给它标「覆盖」）。
- **套用时机与阵营层完全一致**（部署 / 登录 / 保存即时生效），只是取值改成
  `AttributeService.effectiveFor(factionId, professionId)`；`applyTo` 因此多一个 `professionId` 参数。
- **在线即时生效的范围**：改阵营层 → 该阵营在线成员（`applyToOnlineMembers`）；
  改职业层 → 以该职业在场的成员（`applyToOnlineProfessionMembers`，重套时带上该玩家**自己的阵营**）。
- **命令**：`/rp attribute prof get|set|remove|clear <职业>`（与阵营层同一套实现，权限同 `ccnrp.admin.attribute`）；
  `prof get` 会额外列出"正在覆盖阵营层的同 id 属性"。
- **界面**：职业页签的「属性」按钮打开**同一个**弹窗，标题带职业 id；正在覆盖阵营层的行右侧标
  **「覆盖」**（红字）。标记判据与生效判据同源（都是两层 id 的交集），客户端不另写一套。
- **投影**：`professions[].attributes` 已加入 `sendList` 投影——新增配置字段必须同步补投影，
  否则会出现"保存成功但界面看不到"（docs/01 §11.2）。
- **边界 / 如何失效**：①若把覆盖改成"逐运算覆盖"或"两层叠加"，本节契约失效（`layer()` 的返回语义要一起改，
  并同步 `AttributeProfileTest` 的 6 条分层用例）；②新增一层（如玩家级）时必须重写 `layer` 的合并顺序，
  不能在各调用点各拼一遍；③职业层属性**不随阵营变化而失效**——玩家换阵营后职业层仍生效（这是刻意的：
  职业层是"这个角色本身的体征"，与挂在哪个阵营无关），若不希望如此，应在换阵营时清空该职业的属性配置。

## 3. 界面

- **职业（角色）页签**：「属性」按钮打开**同一个**弹窗，编辑职业层属性；覆盖阵营层同 id 的行标「覆盖」。
- **阵营页签**：新增「属性」按钮打开属性弹窗（放在入场电影开关那行之后，不新增纵向行——
  表单在最小面板高度下会撞到提示行）。该行 2.25.3 起只剩「入场全屏黑」一个整行开关
  （「简洁电影」版式开关已删除，见 docs/14 §6）。
- **属性弹窗**：行编辑（属性 id / 数值 / 运算循环按钮）+ 新增行 / 删除行 / 保存 / 取消；
  遵守 docs/01 §10 弹窗三条件（隐藏下层 + Esc 只关弹窗 + 关闭清理输入框），已登记进 §10 表格。
- 视觉一律走 `RpTheme`/`RpButton`/`RpRoundRect`（docs/14 黑白灰军用终端）；选中行文字用 `RpTheme.ACCENT_TEXT`。

# 19 · 数据服务接入（CCNR-Data）

契约真源在 **CCNR-Data** 仓库（`proto/moddata/v1/moddata.proto`）。本模组是它的**唯一模组侧消费者**。
本仓库持有一份 vendored 副本 `src/main/proto/moddata/v1/moddata.proto`，同步方式见 `src/main/proto/README.md`。

---

## 1. 职责边界（读之前先记这条）

| 谁 | 负责什么 |
|---|---|
| **本模组服务端** | 算等级与经验（**权威端**）、决定玩法与门控、决定什么时候上报 |
| **CCNR-Data** | 校验 + 持久化 + 审计 + 变更流。**不实现等级曲线、不重算经验** |
| 客户端 | 只渲染服务端下发的值。**没有等级曲线，因而算不出等级** |

上报是**旁路**：数据服务不可达不影响击杀、部署、阶段推进这些主流程。
但**显示**不是旁路：确认不了的值界面就不显示（见 §3）。

---

## 2. 上报了什么，接在哪

原则是**在每个"汇聚点"接一次**，不在每个上游分支各接一次。

### 2.1 结算 → `RecordSettlement`

唯一汇聚点：`experience/ExperienceService.settleUser`。所有经验变化都经它
（`/rp settle`、`/rp settle all`、死亡、掉线、判死、退役、疏散）。

`reason` 显式贯穿：`settleUser(..., reason)` ← `StatusManager.retire`（它本来就有 `reason`）/
`XpCommand`（`command`）/ `evacuateAlive`（`evac`）。

### 2.2 事件 → `RecordEvent`（11 个汇聚点）

| 事件 | 接入点 | `kind` |
|---|---|---|
| 事件触发 | `event/EventManager.startEvent(int)` | `CONFIG_EVENT_TRIGGERED` |
| 事件结束 | `event/EventManager.endEvent(int)` | `EVENT_ENDED` |
| 清空事件 | `event/EventManager.clearAll()` | `EVENTS_CLEARED` |
| 阶段推进 | `event/EventManager.evaluateAll(Transition)` —— 自动推进与 `/rp phase` 的唯一汇聚点 | `PHASE_ADVANCED` |
| 一局收束 | `event/EventManager.end(String)` | `ROUND_ENDED` |
| 游戏结束 | `event/EventManager.gameOver()` | `GAME_OVER` |
| 部署落位 | `character/CharacterService`（自部署）+ `spawn/SpawnFramework.deploy()` | `CHARACTER_DEPLOYED` |
| 阵亡 | `experience/ExperienceService.emitDeath` | `CHARACTER_DEATH` |
| 击杀 | `experience/ExperienceService.emitKill` | `CHARACTER_KILL` |
| 疏散 | `experience/ExperienceService.evacuateAlive` | `EVACUATION` |
| 刷新波 | `spawn/SpawnFramework.triggerWave` | `SPAWN_WAVE_TRIGGERED` |

- **`ROUND_ENDED` 与 `GAME_OVER` 是两件事**：`/rp gameover` 只播动画，不结算也不结束对局。
- **刻意不上报 `character_alive`**：它是每 60 秒对每个存活玩家发一次的规则引擎内部广播，
  不是对局事件。上报它会让事件量直接翻几十倍。
- **`EVENTS_CLEARED` 同时换 `match_id` 并清空事件流**：「清空事件」在本模组里就是重开一局，
  沿用旧 id 会让两局的事件在数据侧串成一条时间线。

### 2.3 `match_id`

进程启动时生成，每次「清空事件」（重开一局）换新的。在途上报**不回填**新 id —— 那是上一局的事。

## 3. 等级显示：为什么"取不到就不显示"

### 3.1 规则

```
本模组算等级（权威） ──上报/确认──▶ CCNR-Data
        │                              │
        └── GetPlayer / 结算响应 ◀──────┘
                    │
                    ▼
        确认过的值 ──UserXpS2C──▶ 客户端渲染
                    │
              确认不了 ──▶ 不显示等级（不回退本地推算）
```

**为什么不能回退本地推算**：那会让「显示的等级」与「账上确认的等级」成为两个来源。
漂移的现场表现是玩家看到一会儿 7 级一会儿 6 级，而两边单看都是"对的"。

### 3.2 实现

- `sync/RemoteProfiles` 是**已确认值**的镜像：`put()` 只由 `RecordSettlement` 响应、
  `GetPlayer` 响应调用；`forget()` 在上报失败/被拒/连接断开时调用。
- `ExperienceService.pushUserXp(uuid)` 是**等级显示的唯一出口**，读 `RemoteProfiles`；
  取不到就推 `UserXpS2C(..., levelKnown=false)`。
- `levelProgress`（当前等级内的进度 0..1）由**服务端**算；客户端只画。
- `CharacterListS2C` **不再下发 `levelBase`/`levelPow`**，改下发 `userLevelKnown`。
  客户端因此没有任何算等级的材料 —— 这是 §3.1 能成立的前提。

### 3.3 未确认 ≠ 玩不了（刻意划的一条线）

`CharacterManagementScreen` 里：

- **等级读数**（`LV.…`、`CURRENT: …`、职业行进度条）在未确认时**整段不渲染**，不是画成 `LV.0`；
- **席位达标判定**在未确认时**放行**，交给服务端部署入口裁决。

「取不到就不显示」是**显示**规则，不是游戏规则。把两者混起来，一次网络抖动就会变成
"点不动部署按钮"，而玩家根本不知道自己做错了什么。服务端的等级门控
（`CharacterService` 部署入口）不变，仍是本地曲线算出来的权威值。

## 4. 链路实现（`com.ccnrcom.rp.sync`）

| 类 | 职责 | MC 无关 |
|---|---|---|
| `DataLink` | 通道、唯一发送出口、状态码分流、重放、`match_id`、事件流 | ✅ |
| `DataOutbox` | 落盘的 FIFO 重试队列 | ✅ |
| `RemoteProfiles` | 已确认值的镜像（界面等级的唯一来源） | ✅ |
| `DataReports` | MC 感知的门面：只管「没装配就静默跳过」 | ❌ |
| `EventKinds` | 事件种类的**字符串常量**（替代生成的 `EventKind` 枚举） | ✅ |
| `EventPayload` | 载荷写入接口（替代生成的 `RecordEventRequest.Builder`） | ✅ |
| `SettlementDraft` | 结算草稿记录（替代调用方自己 build 的 `RecordSettlementRequest`） | ✅ |
| `command/DataCommand` | `/rp data` | ❌ |

**`EventKinds` / `EventPayload` / `SettlementDraft` 存在的唯一理由是隔离**：它们是
`DataReports` 的公开签名里能出现的全部通信相关类型。原因见 §4.5 —— 这不是风格问题，是崩溃与否的问题。

### 4.1 线程

gRPC 的网络收发在 netty 线程上，但**所有回调都被派发回服务端主线程**
（`DataLink` 构造时拿到 `server::execute`）。于是 `RemoteProfiles` 与所有发包都在主线程发生，
**不需要任何锁** —— 对齐本模组既有的「Level/NBT/网络/渲染必须回主线程」。
反过来说：`DataLink` 的任何方法都**不得**在 netty 线程上被调用。

### 4.2 失败分流

| 状态码 | 处理 |
|---|---|
| `UNAVAILABLE` / `DEADLINE_EXCEEDED` / `ABORTED` / `RESOURCE_EXHAUSTED` / `INTERNAL` / `UNKNOWN` | 入队，等会儿重试 |
| `INVALID_ARGUMENT` / `FAILED_PRECONDITION` / `PERMISSION_DENIED` / `NOT_FOUND` / `UNIMPLEMENTED` … | 记日志**丢弃** |

重放由模组 tick 驱动（每 100 tick 一条），一次只发一条 —— FIFO 顺序是刻意的，
突发重放会在数据服务刚恢复时把它再打一遍。

### 4.3 幂等键与重试

`request_id` 由 `DataLink.nextRequestId(kind)` 统一生成：`<kind>:<matchId>:<递增序号>`。

- **为什么不让调用点自己拼**：格式受服务端校验
  （`[A-Za-z0-9][A-Za-z0-9_.:-]*`、≤128 字符）。第一版按契约草稿拼成 `matchId/uuid/时间戳`，
  被服务端以 `INVALID_ARGUMENT` **全部拒绝** —— 斜杠不在字符集里。症状是"等级一直不显示"
  （确认永远回不来），不是一条明确的错误。
- **为什么不会重复**：`matchId` 是每次启动/重开一局新生成的 UUID，序号在进程内递增，
  因此"同一毫秒内的两次同种事件"也不会撞。**撞了的事件会被数据服务当成重放静默丢掉**，
  所以用时间戳当键是不够的。
- **重试为什么安全**：队列存的是**整条 protobuf 字节**，重放与首发是同一条消息，
  携带同一个 `request_id`。不存在 JSON 往返把某个字段丢了这类失真。

### 4.4 实测踩过的三个坑（改动它们前先读）

1. **`request_id` 字符集**（§4.3）。
2. **重放路径必须与首发共用副作用**：第一版重放走另一条路径，成功时**不回填等级** ——
   数据明明补上了，界面永远不认。现在首发与重放共用 `deliverEvent`/`deliverSettlement`。
3. **永久失败必须出队**：第一版里"不可重试"只在首发路径丢弃，重放路径既不入队也不出队，
   于是队头那条永久失败的请求把 FIFO **永久堵死**，现象与"数据服务挂了"一模一样。
   现在 `finishPermanentFailure` 统一处理。

### 4.5 可选依赖的类型**不许**出现在必然加载的签名里（2.27.0 实机崩溃）

这是本仓库代价最大的一次事故，改 `sync` 包之前必须读完。

**现象**：实机装上**普通 jar**（`ccnr_rp-2.27.0.jar`，不含嵌套的 grpc / protobuf），
服务器启动约 3 秒后崩在 tick 循环里，整局直接没了：

```
java.lang.NoClassDefFoundError: com/google/protobuf/ProtocolMessageEnum
    at com.ccnrcom.rp.event.EventManager.evaluateAll(EventManager.java:361)
    at com.ccnrcom.rp.event.EventManager.onServerTick(EventManager.java:329)
```

**根因不是"忘了判空"**。探测逻辑一直是对的 —— 日志明确打了
`[CCNR-RP] 未找到 gRPC 运行时：数据服务不可用`。错在**上报 API 的签名里带着生成类型**：
老接口是 `DataReports.event(EventKind kind, String summary, ...)`。调用点写的是
「先看 `data == null` 就跳过」，但 JVM 要**执行这次调用**，必须先解析参数类型 `EventKind`，
于是绕过了短路，直接 `NoClassDefFoundError`。

**一句话规则**：只要某个类型出现在**必然会被加载的类**的方法签名/字段/参数里，
它就成了**必然依赖** —— `if (x == null) return;` 拦不住它。
那个 `== null` 之所以看起来像保护，是因为它在**源码**层面确实保护了，
而类解析发生在**它之前**。

**修法**：把通信类型收敛进唯一一个类（`DataLink`），其余代码只见字符串与接口：

- `EventKinds`：`static final String` 常量（编译期内联，跨类加载器安全）；
- `EventPayload`：`setDefinitionId/setPhaseId/.../setPayloadJson(String)` 接口；
- `SettlementDraft`：纯 record；
- `DataLink` 是**唯一**允许 `import com.ccnrcom.rp.data.grpc.v1.*` 与 `io.grpc.*` 的类，
  而它只在 `Class.forName("io.grpc.ManagedChannelBuilder")` 探测通过**之后**才被构造。

**两条门禁把它钉死**（`sync/ProtoIsolationTest`，随 `-PrunTests` 跑，不需要起服务器）：

| 门禁 | 手段 | 挡什么 |
|---|---|---|
| ① `wireTypesAreConfinedToDataLink` | 扫 `build/classes/java/main` 的**常量池字节**，除 `sync/DataLink*` 与生成包外，出现 `com/ccnrcom/rp/data/grpc/v1` 或 `io/grpc` 即失败 | 下一个人把 `EventKind` 写回调用点 |
| ② `reportingWorksWithoutProtobufOnClasspath` | 用**过滤掉 protobuf/grpc/perfmark 的类路径** + `parent=null`（bootstrap）构造隔离类加载器，在里面真的调一次 `DataReports.event/settlement` | 签名里重新混进通信类型 |

② 自带反自欺断言：先确认隔离加载器里**找不到** `com.google.protobuf.ProtocolMessageEnum`，
否则它会在有 protobuf 的环境里永远通过 = 假门禁。① 的反证方式是把它自己从白名单里删掉——
必须变红；`ALLOWED_PREFIXES` 只放 `sync/DataLink` 与 `data/grpc/v1/`。

**改动边界**：

- 新增事件字段 → 加在 `EventPayload` 上，**不要**让调用点碰 `RecordEventRequest.Builder`；
- 上报新数据 → 加 `DataReports` 的重载或扩 `SettlementDraft`，参数只用 JDK 类型；
- 生成包（`data/grpc/v1/**`）**永远是**允许名单里的，它天生就是通信层。

**这条纪律不只管 protobuf**：任何 `transitive = false` 打进 `-all.jar` 的可选依赖
（grpc / protobuf / 将来的任何东西）都适用同一规则。判据是「这个类型会不会被
**普通 jar 也必然加载的类**引用」，而不是「它是不是可选依赖」。

## 5. 构建接线

```groovy
id 'com.google.protobuf' version '0.9.4'          // 构建期生成契约桩到 build/generated（不入库）
```

- **well-known types**：`proto-include/` 作为 **include-only** 目录（`addIncludeDir`）。
  Maven 上的 `protoc` 可执行文件**不带** WKT 搜索兜底（实测 3.21.12 / 3.25.5 / 4.29.3 都报
  `google/protobuf/timestamp.proto: File not found`）；而放进 `src/main/proto` 会生成与
  `protobuf-java.jar` 同名的 `com.google.protobuf.Timestamp`（两个同名类）。
- **依赖走 Forge `jarJar`**，打入 `-all.jar`。每个依赖都 `transitive = false` 并**逐个声明**：
  `jarJar` 配置会解析传递依赖，不禁掉就会把 Guava 33 / Gson / SLF4J / protobuf-javalite 一起嵌进去
  覆盖 MC 自己那份。
- **不做重定位，不用 shadow**：传输层用 `grpc-netty-shaded`（Netty 已预重定位进
  `io.grpc.netty.shaded`，与 MC 的 `io.netty` 不冲突）；Guava **直接用 MC 自带的 31.1-jre** ——
  实测 grpc 1.68.1 全部 jar 引用的 93 个 Guava 成员在 31.1 里逐个存在
  （另有 4 个看似缺失的是继承自 `Future`/`AbstractFuture` 的方法）。
  这样开发期、测试期、实机用的是**同一份 Guava**，避免「本地测试全绿、上线 NoSuchMethodError」。
  若将来升级 grpc 后出现 `NoSuchMethodError`：先确认 Forge 的嵌套层到底加载哪一份 Guava，
  再决定是把 grpc 声明的 Guava 也声明进 `jarJar`，还是回到重定位方案。

## 6. 运维

```
/rp data status          # 链路状态 / 计数 / 已确认人数 / 最近一次错误
/rp data events [n]      # 当局事件流（数据服务不可达时照常可见）
/rp data flush           # 手动投递一条待重放（进度仍看 status）
```

- 权限：复用 `ccnrrp.admin.db`（与 `/rp db` 同类：后端基础设施的诊断口）。
- 队列文件：`world/ccnr_rp/data_outbox.json`。**payload 是 protobuf 字节的 base64，不要手改。**

### 诊断对照

| 现象 | 先看什么 |
|---|---|
| 所有人都不显示等级 | `/rp data status` 的 `state`：`DOWN` = 连不上；`DISABLED` = 配置关了 |
| 个别人不显示等级 | 该玩家的上报被拒（`recentFailures`）；`NOT_FOUND` 是"数据侧无档案"，不是故障 |
| `pending` 一直不降 | `lastError`；若数据服务是好的，看是否卡在一条永久失败的队头上（§4.4 第 3 条） |
| 等级与预期不符 | 数据服务的 `xp_diverged` 告警会打在模组日志里 —— 本地账本与库中记录不一致，**不会被静默对齐** |

## 7. CCNR-PM 的取数契约（改签名前必读）

**CCNR-PM（管理面板）通过反射读本模组的对局数据、并通过反射下发对局指令。**
两边是互相独立的仓库，没有编译期依赖，因此**任何一处改名都不会让任何一边编译失败**——
症状只会是「PM 的对局页签突然变空 / 按钮点了没反应」，且不会有一条明确的错误日志。

### 7.1 PM 依赖的确切入口

读（`RpBridge.matchSnapshot()`）：

| 方法 | 用途 | PM 侧的降级 |
| --- | --- | --- |
| `EventManager.matchStatePayload()` | 对局状态（运行中 / 模式 / 当前幕 / 计时 / 进行中事件）**原样内嵌** | 该块为空 → 界面显示「空窗期」 |
| `EventManager.clock().phases()` | 幕表 | 空表 → 只显示当前幕，切幕按钮置灰 |
| `EventManager.events()` | 事件定义 + `state()` + `enabled()` | 空表 → 只显示运行中的事件，触发按钮置灰 |
| `DataLink.recentEvents()` | 当局事件流（与 `/rp data events` 同一份） | 空表（数据服务未启用时属正常） |

写（`RpBridge.matchAction(...)` 的**白名单**，只认这六个名字）：
`switchPhase(String)` / `triggerEvent(String)` / `endEvent(String)` / `end(String)` /
`gameOver()` / `clearAll()`。

展示名一律走对方的 `DisplayInfo.nameOr(fallback)`（**不要**让 PM 自己读 JSON 字段：
「没配名字时回退成什么」也属于显示契约）。

### 7.2 三条约定

1. **这些方法的签名是跨仓库契约**。要改名/改参数，先在这里改表，
   并在**同一次交付里**同步 `CCNR-PM/src/main/java/com/ccnrcom/pm/integration/RpBridge.java`
   （它有单测与接线门禁，但都是 PM 侧自己的，跨仓库的漂移它看不见）。
2. **`end(String reason)` 的理由字段必须经 JSON 编码，不得字符串拼接**。理由里带一个引号，
   拼接写法就会让**存进数据库的载荷变成非法 JSON**。2.27.1 起改为
   `JsonObject.addProperty(...)` 构造载荷（见 §8.1）。PM 侧固定传服务端常量 `"pm"`，
   但这条纪律对**任何**新载荷字段都成立：一律用 `JsonObject`，不要用 `+`。
3. **PM 不发第二个 gRPC 客户端**。事件流与 match_id 都是本模组的**运行时**状态，
   PM 自己连数据服务只会拿到「已落盘的部分」，与管理员眼前这一局不是同一批数据。
   要给它新数据，就加在这里的公开访问器上，不要在 PM 侧另开数据源。

### 7.3 相关纪律

- 事件流是**本地环形缓冲**，可见性刻意不依赖与数据服务的连通性
  （「上报没上去」与「看得见发生了什么」是两件事）。PM 的事件页签正依赖这一点，
  所以**不要**把 `recentEvents()` 改成「只在连上时才有内容」。
- `EventManager` 的那几个入口都是**服务端主线程**语义。PM 在 `consumerMainThread` 的包处理器里
  调它们，因此没有额外加锁；不要把 `recentEvents()` 移到别的线程去调。

## 8. 已修缺陷（留作回归参照）

### 8.1 `end(String reason)` 的载荷字符串拼接 —— 2.27.1 已修

旧写法：

```java
b.setPayloadJson("{\"reason\":\"" + reason + "\",\"resetToPhase\":\"" + ... + "\"}"));
```

`/rp end <理由>` 的理由由管理员手输，**不含任何转义**：理由里出现 `"` 或 `\`
就会写出非法 JSON，落库后只有到查库时才会发现（上报本身是成功的）。

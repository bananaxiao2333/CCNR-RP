# CCNR-RP 开发经验教训（v2 重构成败复盘）

> 记录 2026-08 一次大重构（删除角色实体 → 职位选择 + 等级解锁 + 统一流程）过程中的真实经验与踩坑，供后续开发避坑。
> 结论先行：全程保持可编译基线、小步提交、交错重构别一次性委托给单个子代理、统一流程用 flag 而非分支、UI 改动以冒烟截图回验。

## 1. 大重构方法论

- **先定数据模型再动手**：删角色实体会波及状态/经验/冷却/刷新/尸体/网络/客户端。动手前先确认底层建模——用 ask_user_question 给选项（彻底删实体 vs 每用户单角色），用户选了彻底删实体，这决定后续所有改动形态。数据模型选错 = 全盘返工。
- **拆解为看板任务**：按依赖排序（数据底座 → 核心重构 → 门控 → UI → 结算 → 收尾），每个任务带 DoD 清单；任务间标注依赖。比一条大 PR 可控。
- **每步编译验证**：compileJava 是最低门禁，每完成一小块就编一次。中途一度让仓库处于无法编译状态，排查成本远高于增量修复。

## 2. 子代理（subagent）用于交错重构的经验

重要教训：把删除角色实体并改 40+ 个文件一次性丢给单个子代理 = 灾难。
- 前台 600s 超时，留下**半迁移状态**（CharacterData/Store 已删，但 StatusManager/SpawnFramework/EventManager/命令/客户端还有约 100 处旧引用），构建直接失败。
- 并行子代理（status/spawn/event/commands/客户端）各自编辑共用工作区，能救但很慢；多个子代理反复跑到 600s 未结束，只能 interrupt 接管。
- 结论：交错重构不要整包委托，适合委托的是文件集不相交、边界清晰的机械改动（如删皮肤类、修某个包的编译引用）。委托 prompt 要给确切的新 API 签名 + 明确的删除/替换清单，并强制不要跑 gradle、只改指定文件、报风险点。子代理经常读太多改太慢，宁可给极紧范围；若它改了 90% 还差一个文件，interrupt 后自己补更稳。共用工作区并行子代理有冲突风险（重复 .add()、同文件两处改），事后要盯编译错误。

## 3. 工具踩坑（本会话高频）

- **run_code 里的字符串转义**：JS→bash→python 多层转义极易出错（l.split 里的反斜杠写进文件会变成非法转义）。含全角/中文/破折号/嵌套模板字符串的 prompt 常报 Expected ',' / Expected a semicolon → 把 prompt 写成纯 ASCII、避免 ${} 和全角字符。
- **edit 工具要求先 read**：file changed since read（多是 spotless 重新格式化导致）→ 先 read 再 edit，别硬试。
- **spotlessApply 会在 build 前重排格式**：改完一段代码后，下一次 edit 大概率撞 file changed；提交前必跑 spotlessApply，否则 spotlessCheck 本地/CI 在 build 里 FAILED。
- **taskboard_checklist / taskboard_move 的 ifVersion**：每次 check/move 都 +1 版本；连续操作必须重新读卡取最新版本，否则 stale version / invalid_transition（todo→in_review 需先 claim 到 in_progress）。只能移到 in_review，done 只能用户确认。
- **删除被删实体的测试**：删了 CharacterData/CharacterStore，对应的 CharacterDataJsonTest/CharacterStoreTest 必须一并删，否则 compileTestJava 失败。

## 4. 模组功能错误模式（典型成因）

- **状态栏/结算只在背包里显示**：客户端 HUD 若只挂在 ScreenEvent.Render.Post（且只对 InventoryScreen），非背包场景不可见。结算逐行要任何时刻可见 → 必须注册为 RegisterGuiOverlaysEvent 的 aboveAll 覆盖层（为此加了 StatusHud.renderXpOverlay）。HUD 常驻 vs 仅背包是两种挂载，别混。
- **%s 与 {0}**：Component.translatable(key, args) 用 {0} 占位；语言包若写 %s 会字面显示 %s。老消息死亡结算 %s +%s …→ 等级 %s 就是活例子。凡走 translatable 一律 {0}，且参数个数要与占位符一致。
- **分支统一 vs 分支增殖**：用户明确征召/自部署/管理员刷人走同一函数，只用 flag 区分行为（跳过开场动画等），不要为征召单开分支、不要再有征召兵阵亡旁白。早期让 settleConscriptDeath 单独算积分→被要求并入 settleUserDown。统一流程 = 唯一入口 + 行为 flag；任何某类身份特殊处理都要三思。
- **强制弹窗 vs 热键开关**：招募邀请原来 onRecruitOffer/onClientTick 强制 setScreen(RecruitPopupScreen)，用户反馈影响战斗。改成不强制弹窗，加开关键 OPEN_RECRUIT，右侧常驻悬浮 HUD 不受热键控制、始终显示。功能是否常驻/常开要问清，别默认全屏弹出。
- **经典 API 变动**：皮肤系统删除后，预览模型 CharacterPreview 用无 textures 的 GameProfile 会渲染默认 Steve 皮肤；要显示玩家本人皮肤 → 用 Minecraft.getInstance().player.getGameProfile()（带 textures）。ItemStack 词条用 g.renderTooltip(font, stack, x, y)（1.20.1 内置重载），避免 TooltipFlag 路径问题。

## 5. 构建门禁

- ./gradlew build -PrunTests（含 compileJava + spotlessCheck + test）是验收基准；-PrunTests 才跑单测（离线默认不跑）。
- 环境：export JAVA_HOME=<JDK21>、export GRADLE_USER_HOME=<共享缓存>；Corpse 编译期依赖走 libs/ fileTree。
- 语言包：zh_cn/en_us 键必须同步；LangFileTest 拒绝值 == 键和漏翻。en_us 的锚点文本可能与 zh_cn 不同（Recruit Offers vs 招募请求），别照抄 zh 的旧字符串当 en 的 old_string。

## 6. 迭代反馈（截图驱动）

- 用户以游戏内截图反馈，比文字更准：K 面板缺装备预览、结算还是旧一条 %s、管理按钮不见了、模型变 Steve、邀请强制弹窗影响战斗等。
- 反馈节奏快，需小步改、编译、部署、回验；并在回复里明确剩余项与优先级，避免一次吞太多。

## 8. 管理面板 GUI / 载荷链路 / 发布流程经验（v2.18.12+，关系管理/经验规则页签沉淀）

### 8.1 页签内控件生命周期（clearWidgets 陷阱）
- RpAdminScreen.rebuild() 第一行就是 clearWidgets()：**所有 widget（含页签自建的 EditBox）都会被移除**。
- 页签自建输入框若只在首次构造时 addRenderableWidget（if (box == null)），下一次 rebuild 后控件即从屏幕消失——
  不渲染、不接收点击/键盘（典型表现 = "无法编辑"）。**必须每次 rebuild 重新注册**，并把手头编辑值用选中态/草稿在重建时恢复。
- 布局基准：页签栏占 py1+42..py1+62，页签内容区必须从 py1+76 起（与各页签 listY1 基准一致），否则内容与页签栏重叠。

### 8.2 服务端嵌套载荷必须解包（静默型 bug，编译测试全过只在真机必现）
- C2S 载荷若是 {action, rule{from,to,type}, original?} 的嵌套结构，服务端**必须先 req.getAsJsonObject("rule") 解包**
  再传给 CRUD 业务方法；直接传整个 req 时方法内读 rule.get("from") 拿到的是顶层（不存在）→ 空列表 →
  必现 "from/to 不能为空"（新增/保存）或 "未找到该关系规则"（删除）。
- 这种"读错 JSON 路径"不抛异常、编译测试全绿，只在真机必现——解析嵌套载荷先解包，并加单测覆盖。

### 8.3 自定义弹层（下拉/补全）的命中与绘制顺序
- 弹层会盖住 widget（EditBox/Button）：**命中必须放在 super.mouseClicked（widget 分发）之前**——在父屏加 overlay 前置方法，
  否则点击弹层项被底层 widget 吞掉；**绘制必须放在 super.render 之后**（置顶），否则被 widget 盖住。
- 点弹层外：收起弹层并 return false 放行到底层正常分发。

### 8.4 文本溢出：像素裁剪与贪心换行
- 列表行文本按 font.width 裁到可用宽度 + 省略号（clip），避免与右侧标签重叠。
  （2.25.2 起这两件事只有一份实现：`RpTheme.wrapText` / `RpTheme.clip`；各界面自写的 6 份同构代码已转调。
  实测教训：**按空格分词的断行对中文完全失效**——中文句子无空格 → 整句被当成一个"词" → 确认框正文
  整行溢出并压到按钮上；弹窗高度又是按 `width/(w-32)` 估的行数，于是高度也不对。断行必须逐字符累计 `font.width`。）
- 入场字幕按像素宽度贪心断行（逐字符累计 font.width，超 maxW 断行）；打字动画跨行连续推进——
  换行只影响视觉分行，时序仍按整行字符数，后续行按下方的完整行数堆叠不重叠。

### 8.5 编辑语义：按"选中的原始规则"定位，别用输入框当前内容
- 管理面板「保存」携带选中规则的原始 from/to（original）→ 服务端按 original 定位**原位替换**（支持改 from/to 不误增新规则）；
  「删除」同样按选中规则定位。缺 original 的旧载荷回退按新值 upsert（向后兼容）。

### 8.6 发布流程约定（用户要求，务必遵守）
- **每次改动**：实现 → 验证（spotlessApply && build && test -PrunTests）→ bump 版本号 → CHANGELOG 顶部补条目 → git 提交。
- mod_version 在 gradle.properties（mods.toml 用 ${file.jarVersion} 自动注入，无需手改）。
- 提交信息带版本：feat/fix/docs: vX.Y.Z <描述>；合并回主干：git checkout main && git merge --ff-only <分支>。
- zh/en 语言包键必须成对新增（LangFileTest 拒绝漏翻/键值相等）；文档与代码同步改（载荷契约先改 docs 再改代码）。

## 9. 配置保存字段语义与全服广播线程纪律（v2.18.32–v2.18.35 沉淀）

### 9.1 多字段实体的保存入口必须"各管各的字段"（本次最大教训）
- **职业这类多字段实体（name/factionId/unlockLevel/selfDeploy/loadout/music/profile/cmdcamScene/radio/radioDisabled）的每个保存入口，必须想清楚它负责改哪些字段**：
  - 表单保存（全量编辑）→ upsert 可以，但**未在表单里的字段要从现有定义继承**（resolveSave：loadout/selfDeploy/radioDisabled 缺省继承原值，见 v2.18.32）。
  - 单字段操作（保存装备 / 部署点 / 无线电）→ **必须 deepCopy + 只替换那一个字段**（`setProfessionLoadout` / `setProfessionSpawn` / `setFactionRadio` 模式），绝不复用全量 upsert。
- **空串/缺省参数是"静默吞字段"的温床**：6 参 `upsertProfession(..., loadout)` 转发 11 参时补 `music=""、profile=""、cmdcamScene=""、radioDisabled=false` → `FactionProfessions.upsert` 对空串执行 `remove()`、对 false 直接覆盖——**每次保存装备都会把音乐/项目简历/CMDCam 场景/无线电禁用开关吞掉**。这类 bug 编译测试全绿、只在真机必现（同 §8.2 嵌套载荷解包，都是"读错/写错路径"的静默型）。教训：**通用 upsert 的重载越少越好；每个调用点按职责选方法，别复用"看起来差不多"的重载**。
- **create 语义要防误覆盖**：upsert 语义的 create 命令对已存在 id 会按空参数覆盖 → create 前先查存在性并拒绝。
- **回归测试**：反射绕过 FMLPaths 构造 FactionManager（Unsafe.allocateInstance + 注入 root/file + reloadFromRoot），直接驱动 `updateFaction`/`setProfessionLoadout` 断言"更新字段被替换、其它字段原样保留"，把静默吞字段变成显式测试。

### 9.2 配置变更全服广播：主线程快照 → 后台构建纯数据 → 回主线程发包（v2.18.33）
- **N 人服不要在主线程逐玩家构建大 JSON / 逐玩家读配置文件**：原实现每次广播 N×4 次文件读取 + N 次大 JSON 构建序列化，人多必卡。改为三段式：
  1. **主线程快照**（只读一次）：玩家列表、逐玩家字段（admin/用户状态——用户表是普通 HashMap 非线程安全、玩家访问只能主线程）、在职统计、CMDCam 场景名、头顶标签 payload。
  2. **有界单线程后台构建纯数据**：各配置文件只读一次；后台只碰冻结对象（factions.root/graph 整替换）、深拷贝快照（managerSettings.toJson）、原子写保证一致性的文件读、Forge 配置值。
  3. **回主线程发包**（`server.execute` 排入主线程）：逐人校验在线后发送。
- **线程纪律核对（docs/01 §9.4）**：后台绝不碰 Level/玩家/实体/用户表；发包回主线程；有界执行器 + daemon + ServerStopping 对称关闭；连续变更 last-wins 合并（overload 保护）；逐人在线校验（世界纪元/连接状态）。
- **配置数据要"所有客户端立即刷新"**：部署点（阵营/职业）、职业装备 loadout、serverconfig（等级曲线/头顶标签）、关系规则等配置变更都要全服广播，别只同步操作者或等客户端自己回拉——管理端 CRUD 后统一走异步 broadcastToAll。

### 9.3 其它
- **复活点管理传送按钮**：管理弹窗每行一个动作按钮（传送/移除）用 `List<int[]>` 记矩形、渲染与点击共用（与 spRemoveBounds 同款），点击发专用 C2S（`AdminTeleportC2S`），服务端权限校验后按维度解析 Level 跨维传送（`teleportTo` 自带维度切换）。
- **新 C2S 包三件套**：RpPackets 内定义（构造/编码/解码/handle）→ RpChannels.register() 注册（id++）→ 服务端静态 handler（enqueueWork + 权限二次校验）。漏注册会在运行时收不到包，编译不报错。
## 10. 配置字段投影与编辑者同步（v2.18.36 沉淀）

### 10.1 「保存后看不到」的诊断顺序（职业 spawn 漏投影案例）
- 现象：管理面板保存职业部署点后重开弹窗仍为空，用户报「无法保存」。
- 排查：① 服务端 setProfessionSpawn 单测 → 落盘正常；② 客户端镜像（sendList 投影）→ 职业 JSON 漏了 spawn
  （阵营有、职业没有）→ 弹窗从镜像读 spawn 永远为空。根因是**投影漏字段**，不是保存失败。
- 教训：**「保存后不显示」先验证服务端落盘，再查客户端镜像投影是否带该字段**；新增/扩展配置字段时，
  必须同步检查 sendList 投影与所有读取它的编辑器（K 面板 / 管理面板 / 复活点弹窗）。

### 10.2 编辑者同步刷新 vs 其余玩家异步广播
- 配置保存后编辑者（管理员）如果也走异步广播，其面板刷新不即时且可能被 last-wins 合并。
- 改为 broadcastConfigAll(editor)：编辑者**同步** sendList+sendManagerState（立即、权威、所见即所得），
  其余玩家异步三段式广播（跳过编辑者避免重复发包）。
- 这是 docs/01 §9.2 服务端权威的落地：配置保存的权威结果必须立刻回灌给操作者，普通玩家可容忍毫秒级异步延迟。
## 11. 可选 mod 适配与"死亡背包"类隐性依赖（v2.24.0 沉淀）

### 11.1 不要把行为正确性建立在另一个 mod 的副作用上
- issue #1「死亡后不会清理背包」的根因不是"少写了一句清背包"，而是**过去根本没有清背包的代码**：
  真正清空背包的是 Corpse 模组（它 `removeDrops()` 把物品收进遗体）。遗体 mod 一移除，这个副作用消失，
  于是暴露出"死亡不掉背包"；而原版恰好有三条路径也不掉：`keepInventory=true`、
  死亡瞬间处于旁观者模式（`ServerPlayer.die` 的 `if (!isSpectator()) dropAllDeathLoot` 跳过）、
  离线判死（没有原版掉落流程）——本 mod 自己还会把未部署玩家强制切成旁观者。
- 教训：**"原版会处理"必须逐条验证**（读原版字节码/源码），并在本仓库补位；否则"降级路径"只是文档里的一句话。
  判据沉淀为纯类 `DeathInventoryPolicy`（可脱机单测），避免以后再靠人肉推理。

### 11.2 可选 mod 适配：先注册名，再能力接口，最后才考虑编译依赖
- "改血量"在装了 FirstAid 时**完全无效**——它把血量换成 8 个部位血量，原版 `generic.max_health` 只用于显示钳制。
  这类适配不能靠猜 API，必须读对方源码确认（本次读了 FirstAid 1.20.x 的 `AbstractDamageablePart`/
  `AbstractPlayerDamageModel`）。
- 适配层的顺序：① **注册名寻址**（原版与 mod 属性走同一条路径，未注册 id 只跳过 + WARN）→
  ② **能力接口 + 纯反射 + ModList 探测**（`PlayerAttributeBridge.FirstAidAdapter`，零编译依赖、失败只记一次 WARN）
  → ③ 只有在反射不可行时才按 docs/01 §8 添加 `compileOnly` jar + fetch 脚本（要同步 mods.toml 与 ProjectMetadataTest）。
- 教训：**任何"只为某个 mod 写死"的分支都是兼容事故的种子**；数据能表达的（注册名 + 数值 + 运算）绝不写进代码。

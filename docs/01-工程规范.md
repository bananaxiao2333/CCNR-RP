# CCNR-RP 工程规范（docs/01）

## 1. 环境与命令速查

```bash
export JAVA_HOME=/opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk/Contents/Home
./gradlew spotlessApply            # 一键格式化（提交前必跑）
./gradlew build                    # 语法（-Xlint:all）+ 风格（spotlessCheck）门禁
./gradlew test -PrunTests          # 单元测试（离线默认不跑，CI 上强制跑）
./gradlew check                    # style + test 聚合验收
./gradlew runServer / runClient    # 开发环境启动
./scripts/fetch-corpse.sh          # 取 Corpse 编译期 jar（libs/，勿提交）
```

## 2. 代码风格（必须遵守）

- 统一 **spotless + palantirJavaFormat**；`spotlessCheck` 是 CI 硬门禁，`spotlessApply` 是唯一格式化入口（勿手改格式）。
- 每个 Java 文件首部必须带 license 头（`config/spotless/license-header.txt`，spotless 自动校验）。
- `.editorconfig`：4 空格缩进、UTF-8、LF、文件尾换行；`json/yml/toml` 2 空格。
- 命名：类 `PascalCase`（纯逻辑类用业务名：`FactionGraph`、`LevelCurve`、`WaveSelector`）；
  常量全大写；包名小写；lang 键 `ccnr_rp.<系统>.<语义>`（如 `ccnr_rp.faction.relation.hostile`）。
- 注释：类的 Javadoc 用中文说明职责；公开方法写清"做什么、何时调用、失败行为"；不做逐行注释。

## 3. 语法检查

- `tasks.withType(JavaCompile)` 已附加 `-Xlint:all`（警告不阻断；本地 `./gradlew compileJava` 自查）。
- **类型安全**：禁止裸 `Map<String,Object>` 横穿系统边界；DTO/record 定型（Gson 用 `TypeToken`）。
- 禁止在 service 层直接操作网络/渲染；MC 类型访问必须收敛在薄适配器（如 `CorpseBridge`、`client/*`）。

## 4. 自动化测试约定

- JUnit5（jupiter），类名 `XxxTest.java`，位于 `src/test/java/com/ccnrcom/rp/`，与主包结构对齐。
- **`-PrunTests` 门控**：离线/无网开发环境 `build` 不自动跑（对齐 CCNR-Com）；CI 与本地验收显式传参。
- **纯逻辑优先**：曲线、图解析、评分、选人、触发器、动画解析一律无 MC import（可脱机直测）；
  涉及 MC 的用例仅测适配器行为（如 NBT roundtrip），不测 Minecraft 内部逻辑。
- 每个系统至少：正常路径 1 例 + 非法输入 1 例 + 边界 1 例；修复回归必须有对应测试（防回退）。
- 语言包一致性由 `LangFileTest` 全局守护（zh/en 键集相等、无原始键）；`ProjectMetadataTest` 守护工程元数据。

## 5. 配置与数据规范

- **分层**：serverconfig toml = 调参常量；`config/ccnr_rp/*.json` = 结构性定义（管理员可编辑）；
  `world/ccnr_rp/*.json` = 运行时数据（系统独占）。
- **原子写**：写 `<file>.tmp` 后 `Files.move(REPLACE_EXISTING)`；损坏文件保留为 `<file>.bak` 并告警。
- **容错**：JSON 解析失败 → ERROR 日志 + 跳过该文件/条目（服务继续）；校验错误消息必须带 `文件:行号`。
- **版本字段**：每个 JSON 顶层 `"version": 1`；加载时向后兼容（未知字段忽略，缺字段用默认值并 WARN）。

## 6. 提交与闸门流程

- 提交信息：`feat: P1 阵营关系系统（阵营/组/关系+命令+测试）`；修复用 `fix:`，文档 `docs:`。
- **阶段闸门**：每阶段完成后依次验证——① `spotlessApply && clean build` ② `test -PrunTests`
  ③ 该阶段 `docs/0X` 验收清单逐项勾选 ④ 通过后才提交并进入下一阶段；失败必须修复后重验。
- CI（main push/PR/tag）等价执行 ① ② 并上传产物；tag 自动挂 Release。

## 7. 权限与错误反馈

- 权限节点：`ccnrrp.admin.{faction,profession,event,phase,spawn,settle,animation,kill}`；无节点时回退 OP≥2（复用 CCNR-Com Permissions 模式）。
- 所有命令失败路径必须回显具体原因（lang 键 + 参数）；禁止静默吞错。
- 客户端与服务端版本不一致：通道握手失败时记录 WARN，禁用联动功能并提示（参考 ChannelSync 模式）。

## 8. 其他硬性约定

- **不改 CCNR-Com / CC-api**；所有改动限于本仓库。
- 第三方运行时依赖（Corpse）必须：`mods.toml` 声明可选 + `libs/` 不提交 + fetch 脚本可复现。
- 事件/刷新/动画钩子签名属公共契约，改动先改 docs 再改代码。

## 9. 开发纪律（提炼自 GFBS-Main 开发规范，适用于本项目）

### 9.1 分析先行，修根因
- 动工前先读目标代码及其相邻的注册、事件、网络、配置、资源与生命周期代码，理解现有架构后再定方案；不得只凭需求描述猜测项目结构直接新增实现。
- 开工顺序：确认现象与需求 → 分析调用链与数据流 → 定位根因 → 明确影响面与兼容边界 → 最小改动方案 → 实现 → 验证；禁止跳过分析靠反复试错碰运气。
- 修复必须针对根因。禁止用强制刷新、重复发包、每帧重建、延时重试、无条件全量扫描等方式掩盖状态错误；确需兜底时兜底也必须有边界、去重、限频和可追踪原因。
- 修改范围必须与任务直接相关。未经明确要求不得改版本号、build.gradle、依赖版本、许可证、发布流程、资源组织、无关代码风格或其他系统，也不得顺手做大规模重构。

### 9.2 服务端权威与网络同步
- 服务端是游戏状态的最终权威；客户端只发送操作意图，服务端必须重新校验距离、视线、权限、目标状态、参数范围与世界有效性；不得信任客户端提交的最终状态，也不得让客户端自行决定需要持久化或广播的结果。
- 网络同步围绕权威实例、增量变化、频道/区块追踪与玩家生命周期设计，避免全维度广播及每 tick 全量同步；晚加入、重进游戏、重新追踪、切换维度与断线重连后都必须获得当前有效状态。

### 9.3 状态、版本与缓存
- 逻辑状态、存档状态、同步状态、渲染状态必须有明确的单向转换与版本关系；加载或重进世界后的正确性不能依赖"重新放一次方块""手动触发更新"或等待偶然的全量刷新。
- 缓存必须声明键、所有者、生命周期、失效条件与内存上限；任何缓存不得成为第二权威源，不得因"命中率高"跳过版本验证，也不得保留已卸载世界的对象。

### 9.4 线程与资源纪律
- 独立线程只处理纯数据和不可变快照，禁止访问 Level、BlockEntity、实体、玩家、NBT、网络对象与渲染对象；世界操作、发包、NBT 读写与渲染提交必须回到各自规定的主线程/渲染线程。
- 禁止为每个设备、实例或音频实例创建独立线程；并发任务必须使用有界执行器、批处理、分片或现有调度设施，必须有过载保护、取消机制、世界纪元校验和关闭流程。
- 资源、线程、监听器、网络追踪、GPU 对象和缓存必须对称创建与释放；世界卸载、维度切换、配置切换、资源重载、服务端停止与客户端断线都属于必须实现的清理路径。

### 9.5 通用性与配置
- 数据驱动优先于硬编码：可由 JSON、注册表、配置、资源或公共接口表达的内容不应写死在类名、ID、固定坐标、固定数量或针对单张地图的条件判断中。
- 通用实现必须考虑未来复用，不能只对当前唯一实例生效；但"通用"不等于无边界扩张，不能借通用化名义创建与本次需求无关的大框架、大版本或 v1/v2 包装。
- 配置开关必须真正改变对应功能的执行路径并阻止无意义开销：关闭后不应继续计算再丢弃结果；默认值应维持现有体验与兼容性；运行时切换必须完成旧模式清理、新模式初始化和必要的状态重放。

### 9.6 质量与交付
- 高频路径应避免每帧分配、装箱、字符串拼接、反射、全量扫描、重复邻居更新、重复网格重建和同帧重复发包；应使用批处理、合并、去重、脏标记、对象复用、空间索引和有界预算，但不能牺牲状态正确性。
- 异常处理不能静默吞错，也不能在高频路径无限刷日志：可恢复问题应输出一次或限频诊断并安全降级；不可恢复问题应保留足够上下文，使日志能定位到系统、实例、世界、区块与状态版本。
- 禁止长期保留占位实现、空壳接口、未接线配置、伪异步、永远不触发的兼容分支和只为通过编译添加的假逻辑；新增公共接口必须至少有一个真实调用方或清楚的既定接入点。
- 修复现有功能时必须保留未被需求否定的原行为（材质、动画、音效、时序、命令、配置、存档与下游兼容）；"修好一个问题但功能消失"不算修复完成。
- 验证至少包括编译、相关测试、修改差异检查和针对原始现象的运行路径检查；编译成功只证明能编译。涉及客户端/服务端边界时验证 Dedicated Server，涉及同步时验证晚加入与重连，涉及状态时验证重进世界。未能在当前环境实际验证的内容必须明确说明，禁止用"应该/理论上"冒充完成。
- Bug 无法稳定复现时，应先根据日志、截图、触发条件、配置模式和调用链建立可证伪的原因假设，再增加最小必要诊断；不能在没有证据时连续改动多个不相关模块。
- 提交前必须检查 git diff 与 git status，确保没有临时文件、构建产物、IDE 配置、测试世界、无关格式化或用户已有改动混入；每次提交保持单一职责，提交说明准确描述实际改动。
- Git 操作严格以任务授权为边界：要求建分支才建，要求提交才提交，要求推送才推送；未经要求不得创建 PR、合并分支、改写历史、强推、打 Tag、发布 Release 或操作 main/master；未经明确批准不得创建或修改 CI/CD 与自动发布流程。
- 文档与注释应描述"为什么这样设计、边界是什么、如何失效"，避免只复述代码表面行为；文档、代码与实际运行结果不一致时必须一并修正。
- 遇到会显著改变架构、行为、兼容性、依赖、版本、构建或交付范围的歧义时必须先询问；普通实现细节可依据现有代码与本文档作出最小、可逆的决定。

## 10. GUI 弹出窗口行为约束（Popup/Modal 统一行为）

管理面板与全屏子界面中的"弹出窗口"（modal）必须统一遵守以下三条行为条件；新增弹窗时先读本节再实现，
并同步下表登记句柄（避免出现"打开后露出下层界面 / Esc 关掉整个面板 / 关闭后残留输入框"之类回归）。

1. **打开时隐藏下层界面、禁止交互**：弹窗打开时上层界面（如管理面板表单）必须完全不绘制、不可交互。
   实现：`Screen.render` 的 `boolean modal = impactOpen || spawnModalOpen || seqModalOpen || radioModalOpen;`
   必须包含该弹窗；`mouseClicked` 在弹窗打开时优先接管并吞掉底层点击，不放行到下层 widget。
2. **Esc 返回上层而非关闭整个父界面**：`keyPressed` 中 `keyCode == 256`（Esc）必须优先仅关闭当前弹窗并返回
   其上层表单，不得落到 `super.keyPressed` 触发 `onClose()` 关闭整个父界面。各弹窗在 `keyPressed` 顶部按
   `xxxOpen` 依次拦截（一次只开一个弹窗，顺序无关）。全屏子界面（`FactionGraphScreen`、`RpAdminScreen`）
   必须保留 `parent` 并在 `onClose` 返回上层；从游戏（非 GUI）打开的首层界面（`CharacterManagementScreen`、
   `RecruitPopupScreen`）Esc 回游戏即可。
3. **关闭时清理专属 widget**：弹窗内通过 `mkBox`/`addRenderableWidget` 注册的输入框（EditBox）必须在关闭时
   `removeWidget` + 清空集合 + `setFocused(null)`（如 `closeRadioModal` / `closeSequenceModal`）；
   纯手动绘制、无 widget 的弹窗（影响确认、部署点）无需清理。

| 弹窗 | 句柄 | 隐藏下层 | Esc 行为 | 关闭清理 |
| --- | --- | --- | --- | --- |
| 影响确认（CRUD 波及） | `impactOpen` | modal 判定 | Esc=取消（等同「否」，不执行 CRUD） | 手动绘制，无需 |
| 保存装备确认 | `saveLoadoutOpen` | modal 判定 | Esc=取消（等同「否」，不发保存包） | 手动绘制，无需 |
| 部署点 / 职业复活点 | `spawnModalOpen` | modal 判定 | Esc=关闭返回表单 | 手动绘制，无需 |
| 无线电管理 | `radioModalOpen` | modal 判定 | `closeRadioModal()` | `closeRadioModal()` |
| 行为序列 / 流程编辑器 | `seqModalOpen` | modal 判定 | `closeSequenceModal()` | `closeSequenceModal()` |
| 关系测定图（全屏） | `FactionGraphScreen` | 全屏覆盖 | 返回 `parent` | 继承 `Screen` |
## 11. 配置保存与客户端同步规范（v2.18.35-v2.18.36 提炼）

### 11.1 多字段配置实体的保存入口字段职责
- 每个保存入口必须明确「负责改哪些字段」：
  - 表单保存（全量编辑）→ 允许 upsert，但**未在表单中的字段必须从现有定义继承**（缺省继承原值，见 resolveSave）。
  - 单字段操作（保存装备 / 部署点 / 无线电）→ **deepCopy + 只替换该字段**（setProfessionLoadout / setProfessionSpawn / setFactionRadio 模式），禁止复用全量 upsert。
- **禁止用空串/缺省参数调全量 upsert 做单字段更新**：空串会触发字段 remove、false 覆盖开关 → 静默吞掉其它配置（编译测试全绿、只在真机必现）。
- 通用 upsert 的重载越少越好；每个调用点按职责选方法，别复用「看起来差不多」的重载。
- create 语义必须防误覆盖：对已存在 id 先拒绝，不得用 upsert 覆盖已有配置。

### 11.2 配置变更后的客户端同步
- **编辑者立即同步全量刷新**：配置保存成功后，操作者（有编辑权限的管理员）必须**同步**拿到全量数据
  （sendList + sendManagerState，所见即所得），不得依赖异步广播（last-wins 合并下可能被延迟/合并）。
- **其余玩家异步广播**：多人服用三段式（主线程快照 → 有界单线程后台构建纯数据 → 回主线程发包），跳过编辑者避免重复发包。
- **客户端镜像投影必须随配置字段同步补全**：sendList 是手工字段投影（factions/professions/...），
  新增或扩展配置字段时，必须同步检查该投影与各编辑器回显（K 面板 / 管理面板 / 复活点弹窗），
  否则出现「保存成功但界面看不到」（如职业 spawn 漏投影 → 复活点弹窗永远为空）。
- **诊断顺序**：界面「保存后不显示」→ 先单测/日志验证服务端落盘，再查客户端镜像是否携带该字段，避免误判保存失败。
